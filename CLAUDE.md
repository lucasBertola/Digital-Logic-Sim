# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Digital-Logic-Sim — a minimalist digital logic simulator (Sebastian Lague's project). Users build circuits from a small set of built-in chips (NAND, tri-state buffer, clock, memory, displays, buses, etc.), package them into custom chips, and simulate them in real time. This working copy is a fork ("electronniqe simu").

### Regression bench (`Assets/Editor/Bench/`, `runTests.bat`)

Editor-only, source-level tests that run **in parallel** (one case per thread, `Parallel.ForEach` over all cores) and fast (~3.5 s for 142 cases on 16 threads). `runTests.bat` launches the editor in interactive mode (`-executeMethod DLS.Bench.RegressionBench.Run`), prints the summary (`Builds/tests-summary.txt`, full log in `Builds/tests.log`) and exits 1 on any failure; `runTests.bat record` re-records the goldens. Refuses to start while an editor is open.

- **Fixtures** are copies of whole projects committed under `TestData/Bench/<project>/` (currently `PC`: the user's 39 chips — CPU, ALU8, RAM256, registers, latches, generated packages…), loaded by `BenchProject.LoadLibrary` exactly like `Loader` does. They are **outside** the user's save folder and never touched; to refresh them, copy the project folder from `%%APPDATA%%\..\LocalLow\<company>\<product>\Projects\PC` and re-record.
- **Goldens** (`TestData/Bench/Golden/<project>/<chip>.json`, `GoldenRunner`): per chip, a seeded random stimulus (60/45/30 steps of 4 ticks by size, clock driven by the harness: `forcedClockState` for a CLOCK component, alternating 0/1 for an input named like a clock) and the recorded value of every output pin **and of every output pin of the top-level sub-chips** ("probes": the CPU has no output pin, its registers/ALU/bus are what a regression shows up on). Recording plays the stimulus three times with different sim seeds and only asserts the values that agreed (`stable` / `probeStable` masks): a race resolved at random or a floating bus is not a spec. Verification replays with the recorded seed and compares. An interface or sub-chip change reports "re-record".
- **Unit cases** (`UnitCases.cs`, built from scratch with `ChipEmitHelper` on a builtins-only library): NAND truth table, chain settling, SR latch, unconnected input reads 0, VCC/GND, tri-state rules (driven wins, disabled buffer takes its net, conflict random), floating is noise, clock period, forced clock, KEY chip via virtual keys, merge/split, seeded determinism, live modification through `Simulator.Add*/Remove*` + `ApplyModifications`.
- **Fixture refresh**: the fixture is the user's live `PC` project copied on 2026-09-27 (the CPU now has a builtin CLOCK wired to the three registers instead of a `clock` input; `Fixture.ClockLevel/ClockCycle` drive it through `forcedClockState`). The clocked-loop case is the user's running montage (control lines held: every cycle A = A + 1, MAR = A + 1; We_RAM pulsed after the cycle settles). Note for the user's benefit: with We_RAM HELD high the RAM also captures the transients of the A → A + 1 transition (RAM[15] = 32 while A goes 15 → 16); that is the montage's behaviour, not a simulator error.
- **Directed cases** (`DirectedCases.cs`, on the fixture chips): hand-written sequences with KNOWN expected values, asserted after a generous settle (6 ticks) so they test the function, not the tick latency the goldens already pin — Registre8 (load on the clock, hold, OE, reset), Tampon8, MOT8, RAM4/16/64/256 (write three addresses, read back, Cs), PC (20 cycles, wraps at 16), Bascule D (master/slave: D sampled while the clock is high, shown after the FALL), VerrouD (transparent latch), the **CPU micro-program** (A←5, B←3, A+B on the bus, MAR←9, RAM[9]←bus, bus←RAM[9], A←bus, A−B; registers probed by their labels "Registre A"/"Registre B"/"MAR"), and exhaustive checks of every combinational chip against a model: ALU8 (all 8 ops: ADD, SUB, INC, DEC, A, AND, OR, XOR; C = adder carry, i.e. "no borrow" for SUB/DEC; V = signed overflow of the adder; N, Z) on chosen operands, ALU4 unchained exhaustively, Add4/FullA/HalfA, the 4-bit bitwise chips, Dec-2-4, the three MUXes, 4MUX4-1, and every generated gate package. The ALU op table and the register timing were observed once with a throwaway probe, sanity-checked, then hard-coded.
- **Builtin cases** (`BuiltinCases.cs`, builtins-only library, chips the fixtures never use): PULSE (one pulse of the set width per rising edge; a floating input is noise, so the floating-output check uses width 0), ROM 256x16 (output 0 = high byte), the builtin RAM (write on the rising edge, reset), BUZZER (`SimAudio.targetAmplitudesPerFreq` after `NotifyAllNotesRegistered`), 7-segment and LED (the display sub-chip's input pins), RGB and DOT displays (write → back buffer, refresh → visible, reset), buses of the three widths with two 3-state drivers and a terminus, 8↔1 and 8↔4 merge/split round trips. `UnitCases.Build` accepts `"NAME:8"` / `"NAME:4"` for multi-bit dev pins and `Builder.Data(id)` exposes a sub-chip's internal data (ROM contents, pulse width, key).
- **Live-project cases** (`ProjectCases.cs`, run **serially** after the parallel batch because they use `Project.ActiveProject` and the shared modification queue): a real `Project` with its **simulation thread** on the fixture project — player input states on the dev pins, `Project.TickMainThreadForTests()` (the part of `Update` the sim handshake needs: publish the input pins, bump the frame count), results read back from the dev pins' synced `State`; Add4 from inputs, then a chip switch to Registre8 and a clock cycle.
- **"reloads clean"** per fixture chip: `DevChipInstance.LoadFromDescriptionTest` then `DescriptionCreator` back, must be JSON-equivalent (the red "unsaved" star regression).
- **Rule from the user (2026-09-27): a failing test is never edited to pass — it means the code broke; new behaviour gets a NEW test.** And whenever you meet a case that is not tested and you are not sure it works, not sure your change did not break it, or you had an idea that would have broken it: ADD THAT CASE TO THE BENCH, immediately, so it is not forgotten. Optimisations must hold for every circuit, not just the one being measured; if one breaks another kind of circuit, it is not done.
- **Every case is seeded** (`Simulator.ResetForTests(seed)`): all randomness of a run comes from one per-thread stream (`testRng` → PCG per step: `RandomBits16`, `RandomBool`, `RandomIndex` for the unready-chip pick, `NextBytes` for RAM init), so a run is exactly reproducible and there are no flaky tests. Any new random draw in the simulator MUST go through those helpers, never through `Simulator.rng` directly.
- **Thread-static simulator state**: to run cases in parallel, the per-run statics of `Simulator` (`simulationFrame`, `stepsPerClockTransition`, `forcedClockState`, `needsOrderPass`, `canDynamicReorderThisFrame`, `prevRootSimChip`, PCG state, `testRng`) and `SimKeyboardHelper.virtualKeys` are `[ThreadStatic]`. The live app only ever touches them from the sim thread (plus the harness under `RunWithSimulationPaused`, which parks that thread), so nothing changes for it. Any new per-run static in the simulator must be `[ThreadStatic]` too, and `CircuitTester.BuildIsolatedSim` is not thread-safe (it rewrites `lib.SimOverride`): build under `GoldenRunner.buildLock`.
- Loading a chip for a test must not need `Project.ActiveProject` (`RegenerateParentChipNamesHash` takes the library).

### Editor entry point and startup behavior

`UnityMain` (`Assets/Scripts/Game/Main/UnityMain.cs`) is the **only** MonoBehaviour driving the app. In `Awake` it wires up audio and calls `Main.Init`; in `Update` it calls `Main.Update` every frame. Its many public fields (`testProjectName`, `chipToOpenA/B`, `openInMainMenu`, audio test vars, etc.) are editor-only dev knobs set on the scene object:
- In the editor, if `openInMainMenu` is false it auto-opens `testProjectName` / the chosen startup chip — set these to skip the main menu while developing.
- In a build it always starts at the main menu.

Domain reloading is disabled in the editor, so **static state does not reset between play sessions**. `UnityMain.ResetStatics()` manually resets the statics of `Simulator`, `UIDrawer`, `InteractionState`, `CameraController`, and `WorldDrawer`. Any new subsystem that holds static state must be reset there too, or it will carry stale data across runs.

## Architecture

The core idea: a chip exists in **three parallel representations**, and most features touch all three. Understanding this split is the key to the codebase.

1. **Description layer** — `DLS.Description` (`Assets/Scripts/Description/`)
   Plain serializable data classes: `ChipDescription`, `SubChipDescription`, `PinDescription`, `WireDescription`, `PinAddress`, `ProjectDescription`, `AppSettings`. This is exactly what gets saved to / loaded from JSON. It has no behavior and no Unity dependencies beyond basic types. The `ChipType` enum (`Types/SubTypes/ChipTypes.cs`) enumerates every built-in chip; `ChipTypeHelper` classifies them (e.g. bus vs. non-bus).

2. **Game / editing layer** — `DLS.Game` (`Assets/Scripts/Game/`)
   The interactive runtime model. `DevChipInstance` is the chip currently open in the editor; its elements (`SubChipInstance`, `WireInstance`, `DevPinInstance`, `DisplayInstance` in `Game/Elements/`) implement `IMoveable` and carry placement/interaction state. `Project` (`Game/Project/Project.cs`) is the top-level session object: it owns the `ChipLibrary` (all available chip descriptions), the `chipViewStack` (a leftover of the upstream "view mode", which this fork **removed** — the stack always holds the one chip being edited, `CanEditViewedChip` is always true), the **navigation history** (`navHistory`: every chip landed on; mouse back/forward buttons `KeyCode.Mouse3/Mouse4` step through it like a browser, `RecordVisit` / `NavigateHistory`), save/rename/delete orchestration, and the **simulation thread**. `DeleteChip` on the chip being edited returns to the most recent chip of the history that still exists (deleted names are purged from `navHistory`), a blank chip only when there is none. **Undo is strictly per chip**: `GlobalUndo/GlobalRedo` just call the edited chip's `UndoController`; Ctrl+Z must NEVER switch chip (a cross-tab timeline existed and was removed at the user's request). `ActivateEditChip` / `SetNewActiveDevChip` clear every element's `IsSelected` flag: a fresh controller has an empty selection list, and the renderer draws selected elements from that list, so a stale flag made the element invisible (its wires stayed). `ChipInteractionController` and the classes in `Game/Interaction/` handle input, selection, undo (`UndoController`), and placement.

3. **Simulation layer** — `DLS.Simulation` (`Assets/Scripts/Simulation/`)
   `SimChip` / `SimPin` / `PinState` are the runtime execution graph, built from a `ChipDescription` by `Simulator.BuildSimChip` (recursive). `Simulator` (static) runs one sim step over the tree.

### Data flow between the three

- **Load**: JSON → `ChipDescription` (Loader) → `DevChipInstance` (via `DescriptionCreator` / `DevChipInstance.LoadFromDescriptionTest`) for editing, and `Simulator.BuildSimChip` → `SimChip` for execution.
- **Save**: `DescriptionCreator.CreateChipDescription(devChip)` reconstructs a `ChipDescription` from the live `DevChipInstance`, then `Saver` writes JSON. `UnsavedChangeDetector` / `Saver.HasUnsavedChanges` compares live vs. last-saved description.
- **Runtime edits** (add/remove subchip, pin, wire; edit ROM/key/pulse/LED): the Game layer mutates the `DevChipInstance` **and** enqueues a corresponding change on the `Simulator` so the running `SimChip` stays in sync — see the `Notify*` methods in `Project.cs` and the `SimModifyCommand` queue in `Simulator.cs`.

### Simulation threading model (important)

The simulation runs on a **dedicated background thread** (`Project.SimThread`), separate from Unity's main thread, targeting `Prefs_SimTargetStepsPerSecond` ticks/sec. Consequences to respect when editing sim or game code:

- **Never mutate the `SimChip` graph directly from the main thread.** All structural changes go through `Simulator.Add*/Remove*`, which enqueue onto a `ConcurrentQueue<SimModifyCommand>`. `Simulator.ApplyModifications()` drains the queue **on the sim thread** at the top of each step.
- Any structural change sets `needsOrderPass = true`. The next step then **recompiles** the root's `SimProgram` (see below) before running; a compile of the CPU chip (63 000 sim chips) takes a few tens of ms, so it only happens on edits.
- The main thread reads sim results via `ViewedChip.UpdateStateFromSim(...)`, synced once per main-thread frame. Reads of pin state can transiently be out of sync (threads race) — sim code deliberately swallows "pin not found" exceptions rather than locking. Keep that tolerance in mind.
- `debug_runSimMainThread` in `Project.cs` forces the sim onto the main thread for debugging; `debug_logSimTime` logs step timing.

### How the simulation actually steps

The `SimChip` / `SimPin` tree is only the **structure** (what the editor addresses, modifies at runtime and reads for display). A step runs on its compiled form, `SimProgram` (`Simulation/SimProgram.cs`), rebuilt by `Simulator.RunSimulationStep` whenever `needsOrderPass` is set or a different root is stepped:

- **Slots.** Every pin resolves to a slot in one contiguous `uint[]` of pin states. A pin fed by exactly one source *aliases* its source's slot (no copy — a signal crossing custom-chip boundaries costs nothing), a pin fed by several sources is a **merge node** with its own slot, a builtin output pin or a root input pin owns a slot, an unconnected pin gets a slot holding a **driven 0** forever (`PinState.LogicLow`; it held "floating, low" until 2026-10-03: logic read it as 0, but a merge / split / enabled buffer copied the floating flag along — the user's ALU4 shifters, whose unconnected `C_in` went through a MERGE 1->4, showed a flickering 4-bit OUT; bench `UnconnectedCases.cs`, `Assets/Editor/FloatProbe.cs` lists the floating component outputs of a save-folder chip). Custom chips therefore vanish from the step. `SimPin.State` is a property reading the slot (before compilation, a local value), so everything that looks at pins (`UpdateStateFromSim`, the harness probes, tests) sees live values without any write-back — but pin state can no longer be written by `ref`; use `pin.State = PinState.Make(bits, tri)`.
- **Gates.** Every builtin chip is a `Gate` (struct, SoA arrays) reading and writing slots directly; the per-chip behaviour lives in the `switch` of `SimProgram.Step` (add a new builtin's logic there). Bus origins are wires (output aliases input), termini and pure displays (7-seg, LED) have no gate at all. Merge nodes are gates too (`MergeType`): per-bit, a driven source beats a floating one, driven sources in conflict are resolved at random for the step, all-floating stays floating; then floating sources on a driven bit are written back with the net's value (that is how a disabled 3-state buffer's output pin reads its net) and the winning source is recorded in `latestSourceID` for the wire colouring.
- **Activity.** A step only runs the gates whose inputs changed: a dirty bit per gate (`ulong[] dirty`, plus a summary word per 64 words `dirtyTop` so a step and `IdleSteps` scan 11 words, not 700; scanned with a de Bruijn lowest-bit table), set by whoever writes one of its input slots to a different value (`Write` → `MarkConsumers`, slot → consumer gates CSR), cleared when it runs, in schedule order, so a change made by an earlier gate is seen in the same step and one made by a later gate (feedback) on the next. Root input pins are change-detected against a shadow copy at the top of the step (they are written from outside). Gates with a life of their own re-arm themselves (`SetDirty(k)`): clock, key, buzzer, a merge with a conflict (re-drawn at random each step), a pulse counting down. An edited ROM (`SimChip.InternalStateEdited`, set by `UpdateInternalState`) re-runs its gate. A step where nothing changes costs nothing.
- **Idle steps are skipped (live sim thread only).** `Simulator.RunSimulationSteps(root, inputs, audio, maxSteps)` runs one real step, then asks `SimProgram.IdleSteps` how many steps can pass with nothing to do — no pending gate, root inputs unchanged (`CopyPlayerInputs` re-copies them first), no ROM edit, no keyboard version change — and bounded by the next event: the next clock transition (the step whose frame is the next multiple of `stepsPerClockTransition` must be a REAL step, so `period - frame % period - 1`), and the next noise re-draw (accumulator). The skipped steps only advance `simulationFrame` and the noise budget; the state is provably the same. The sim thread batches 256 steps when the target rate is ≥ 100 000/s (`Project.SimThread`, "paced" otherwise: one step at a time so the target rate is honoured, and single-stepping while paused). **Latency of an outside input during a skip span ≤ one clock half-period or 256 steps**, i.e. a fraction of a millisecond. For this to be possible, CLOCK gates no longer re-arm every step: `Step` marks them when the level changes (`lastClockLevel`, also covers `forcedClockState`); KEY gates are marked when `SimKeyboardHelper.Version` changes (bumped by `RefreshInputState` every main frame and by `SetVirtualKeys`); a BUZZER makes the program never idle (`HasBuzzer`: its note must be registered every step). Tests step one by one (`RunSimulationStep`), so the goldens never see skipping; the batched path is covered by dedicated cases: CPU batched vs single (and B loaded between batches while the clock runs), clock + pulse checkpoints, a key press between batches, a bus conflict never idles, and the "game" case (clock running, input moved at chosen steps, compared at checkpoints).
- **Frame counter wrap** (`Simulator.WrapFrame`): at 300 000+ steps/s an int overflows in two hours; above 1e9 the counter is reduced by a multiple of `200 × stepsPerClockTransition`, which keeps the clock phase (frame / period parity) and the reschedule cadence (mod 100). Case "frame counter wrap keeps the clock phase".
- **Quiet propagation**: a stateless gate (NAND, split/merge bit chips, 3-state buffer, merge node) fed only by never-driven slots has constant outputs, marked quiet too (compile, in schedule order). The user's two unconnected RAM256 used to make 4 096 latch NANDs read noise through the SPLIT of their unconnected D_in.
- **Noise (user rule, 2026-09-27: "a floating line may change randomly about once a second").** A floating line carries NO value in the slot (tri flags set, bits 0, `PinState.FloatingLow`): a disabled 3-state buffer, a floating pulse output, a merge with no driver all write that. Noise appears where LOGIC reads a floating bit: the reading gate (NAND, pulse, RAM/display/ROM/buzzer inputs, a buffer's enable — `In()` / `Noisy()`) substitutes random bits and joins the noise list (`ArmNoise`, by canonical gate id), from which `noiseCount / NoisePeriod` gates are re-run per step at random (`NoisePeriod = 1024`: a few times a second at a few thousand steps/s; the display draws a floating pin as flicker itself, `PinInstance.GetStateCol`). A gate leaves the list when it re-runs without reading a floating bit. Slots nobody ever drives (unconnected pins, `quiet[]`) read as a quiet 0, never as noise, and are DISPLAYED as a driven 0 too (`SimPin.DisplayState`, used by `DevChipInstance.UpdateStateFromSim`: an empty output pin used to flicker; only a line that can be driven but is not — a disabled buffer — flickers) — the optimiser's `Extract` and the "unconnected input reads 0" rule rely on it. Values read from a possibly-noisy 16-bit slot are masked before indexing memories (`& 0xFF`). This replaced "noise re-drawn every step at the source": the user's RAM256 has 2 048 disabled buffers, and re-drawing them every step made 8 800 gates run per step for nothing visible.
- **Order.** Gates are emitted by walking the tree exactly as the original stepper visited it: at every level the sub-chips run in the order they become ready (all their inputs produced by siblings already run), and when none is ready (a feedback loop) an unready **non-bus** chip is picked at random and runs on last step's values (`Emit`, the `remaining` / `nonBus` O(1) pick lists). A merge node is emitted right before the chip that owns the pin (input pin) or at the end of it (output pin). So the tick-level timing of latches, registers and buses is the same as the tree walker's, and every 100 steps the random picks of a few feedback levels are re-drawn (`Reschedule`: 16 random chips among those whose level has a pick and whose subtree is ≤ 2048 gates — the CPU root level (bus loop) would cost 4 ms to re-emit and is not a latch race — each subtree re-emitted IN PLACE in its fixed-length segment of the schedule, hot arrays and pending dirty bits updated for that segment only; the noise list is by canonical id) so race conditions vary as before. A full re-draw of the CPU schedule costs ~4 ms, which at 100 000 steps/s was half of the step cost; the partial one is negligible. Compile cost is O(pins + wires); the schedule is a permutation of the gate array, copied so the step loop is sequential in memory.
- **NAND wake-up filter** (`MarkConsumers`, per consumer entry `slotConsOther` / `slotConsOut` precomputed AFTER the slot renumbering): a NAND whose other input is a driven 0 and whose output is already 1 is not woken — it cannot change. At a clock edge that is most of a RAM's latch-input gates. (Precomputing before the renumbering read wrong slots; the 3xAND3 golden and exhaustive case caught it.) Case "nand with a controlling 0 on the other input".
- **NAND + inverter fusion** (`FuseInverters`, `NandNotType` / `NopType`): a NAND whose only consumer is an inverter (NAND with both inputs on it — every AND/OR/NOR the user builds ends that way) runs the inverter in the same go; the inverter gate becomes a no-op. Exact, because the inverter always ran right after in the same step; required: the inverter is scheduled after the NAND and every level from their common ancestor down to each of them is free of random picks, so a reschedule cannot reorder them. 4 287 pairs in the user's CPU.
- **Common-gate elimination** (`EliminateCommonGates`, after the fusion; the consumer lists are rebuilt after both): two NANDs / NAND+inverter pairs with the same input slots compute the same value at all times when (a) their chains up to their common ancestor are free of random picks (their relative order is fixed) and (b) each input is produced outside the common ancestor's subtree (both read the same value, fresh or one step old), or inside it by a gate that precedes the first one and whose own chain to the ancestor is cut-free. The second gate becomes a no-op, its consumers read the first, and its pins are re-bound to the first's slots so the display stays exact. Several representatives are kept per key: a gate that cannot merge with the first one (e.g. a register's splitter, common ancestor = the CPU level with its random pick) may still merge with a later one — without that the RAM's 256 splitters merged or not depending on the compile-time random order. The user's 64 RAM4 decoders all decode the same two address bits, and the 3 × 256 word splitters split the same bus: 3 686 gates merged in the CPU (1 087 NAND, 1 834 NAND+inverter, 765 splitters).
- **Burst kernel** (merged 2026-10-03): `Simulation/SimKernel.cs` runs the pending NAND / NAND+inverter / no-op gates of a step (Burst 1.8.19, direct call with a `StepCtx` of pinned arrays) and hands every other gate back to `SimProgram.RunOne` (other builtins, a gate in the noise list, a NAND reading a non-quiet floating line), then resumes after it — same order, same marks, same random draws, so it is interchangeable with the managed loop (`SimProgram.UseBurst`, thread-static for tests; `BurstEnabled` global, `-noBurst` in SimBench / LiveRate). A program whose kernel calls run fewer than 2 gates per hand-back (the RUN FAST tree: models only) is switched to the managed loop, with one kernel step in 256 to re-measure. Burst AOT works for the Windows player without the MSVC tools. Measured: ×1.7 per gate run (exe: 39 → 23 ns); the fixture CPU batched like the sim thread ×1.27–1.31 in the exe (self-test line); CPU_2 live in the editor +2..13 % (the editor's Mono is faster, and 98 % of steps are skipped idle steps); RUN FAST unchanged. Bench `BurstCases.cs` (every slot after every step, burst vs managed, 6 fixture chips + the RUN FAST tree; a stale-word mutation fails all of them) + a self-test check.
- **Do not** replace the hierarchical order by a flat topological sort with random gate cuts: it was tried, and in the CPU's bus loop the random cuts land on long combinational paths (the ALU carry chain), so a signal needs several steps to settle instead of one or two — the directed CPU case caught it.
- All randomness (floating noise `RandomBits16`, merge conflicts `RandomBool`, forced picks `RandomIndex`, RAM init `NextBytes`) comes from the per-thread PCG stream reseeded each step from `testRng ?? rng`, so a seeded run is exactly reproducible.
- The state array is reused across recompiles of the same root (grown when needed) and each pin keeps its slot index, so a main-thread read racing a recompile at worst sees a stale value, never an exception.

## Built-in chips

To add or change a built-in chip you typically touch several places, kept in sync manually:
- `ChipType` enum (`Description/Types/SubTypes/ChipTypes.cs`) — the identity.
- the `switch` in `SimProgram.Step` (`Simulation/SimProgram.cs`) — its simulation behavior (a chip with no output pin and no side effect needs no case: its input pins carry the values).
- `BuiltinChipCreator` (`Game/Project/BuiltinChipCreator.cs`) — its description (pins, size, colour, display).
- `BuiltinCollectionCreator` — which collection / starred list it appears in for new projects.
- Possibly `ChipTypeHelper` if it needs special classification (e.g. bus handling).

**Existing projects don't get new builtins for free**: `ProjectDescription.ChipCollections` is saved per project, so a chip added to a default collection only shows up in *new* projects. `BuiltinCollectionCreator.LateAddedBuiltins` + `AddMissingLateBuiltins` (called from `Loader.LoadProjectDescription`) backfills a new builtin into its collection, but only when it is absent from *every* collection — so a chip the user deliberately removed is never resurrected. Add new post-fork builtins to that list.

**`ChipType` enum values are serialized** (`ChipDescription.ChipType`, an int in the JSON), so only ever APPEND to the enum.

### VCC / GND (constant sources)

`ChipType.Vcc` / `ChipType.Gnd` — no input pins, one 1-bit output permanently held HIGH / LOW (`SimProgram.Step`, alongside CLOCK which is likewise sourceless; a zero-input chip is always ready). They are **components, not I/O pins**, so they never appear in the chip's interface — that is the point: they let a circuit hard-wire values (LUTs, tri-state ROM matrices, tie-offs) without inflating its input count. `ChipTypeHelper.IsConstantType` classifies them. They are in the `BASIC` collection and, being builtins, are automatically in the Ask Claude `add_components` palette (described in `CircuitExporter.BuiltinDesc`).

### RUN FAST (modules simulated by what they do)

User, 2026-10-03: right-click on empty space > **RUN FAST** runs the viewed chip with its modules replaced by behavioural models; cached for the next time; any edit / chip switch leaves it; the preferences' frequency is the fast one (the sim thread just steps another root). Measured on the user's CPU_2 (chenillard, 70 steps/tick): 61 883 gates → 65; core 41 → 466 kHz (×11.4, `Assets/Editor/FastBench.cs`), app sim thread 44 → 313 kHz (×7.1, `LiveRate.cs -rateFast 1`; the rest is the sim-thread loop overhead per batch). Pieces:
- `ChipType.FastModel` (appended, internal, never saved): a `SimChip` leaf with only its pins and a `FastModel` (`Simulation/FastModel.cs`); `SimProgram` runs it as ONE gate (`Run()` maps the input pin states to the output states; `RerunNextStep` asks for a run on the next step).
- `FastBuilder.Build` (Game): the tree of the chip where every sub-module with a model is a leaf, the others built as usual and searched one level down. Combinational module ≤ 16 input bits → `LutModel`, a truth table computed by the real simulator over every combination (exact by construction, floating outputs included), re-checked in a shuffled order. Sequential module → `FastTemplates`: register / flip-flop (edge, LOAD, sync / async RESET, OE, Q'), counter (+1 / load = jump), RAM (written while WE is active, OE / CS, an address on one pin or 1-bit pins numbered by name). Pin roles come from names + widths; every option is CO-SIMULATED against the gates on random stimulus (state synchronised through the pins first) and rejected at the first difference, and the state read / write procedures are round-trip checked. A module holding a clock, key, display, buzzer, ROM, builtin RAM or pulse is never modelled. Decisions cached by structure hash (`FastCache`, saved as `<project>/FastModels.json` by `FastCacheFile`, hand-written JSON).
- Faithfulness, learnt on CPU_2: a register model samples D / LOAD / a sync reset while the clock is at the level BEFORE the edge and applies them at the edge (master-slave: a neighbour's new output must not race through — the user's PC counted wrong without it), and its OUTPUT shows the new state one step after the edge (clock-to-output delay: the user's RAM WE is an AND of clock phases that drops in 1-2 steps, while their registers change later; an instant register output let the RAM see the new address with WE still high). Combinational tables are instant, so glitches inside a module vanish (the documented price; the gates mode stays the reference).
- `FastState.CopyIn` / `CopyOut`: the state between the gate tree and the fast tree, walked together by sub-chip ID — builtins copy outputs + internal state, a sequential model reads / writes its state through the pins of an isolated copy of the real instance (`FastTemplates.ReadLive` / `WriteLive`, only the words that changed are written back), each model's outputs are seeded at the transfer (a reader must not see 0s until it first runs).
- `Project.StartFastMode` (built on the next `Update` so "Preparing fast mode..." shows; sim paused), `StopFastMode` (state back to the gates), `rootSimChip` / `ViewedSimChip` follow the fast root; leaves on `DevChipInstance` edits of that chip (`NotifyChipEditing` in AddNewSubChip / AddNewDevPin / AddWire / Delete*), `ActivateEditChip`, `SaveFromDescription`, the ROM / key / pulse / LED notifications and the memory editor. `ContextMenu` RUN FAST / STOP FAST, `BottomBarUI.DrawFastModeIndicator` pill + toast.
- Bench `FastCases.cs` (combinational and sequential equivalence on the fixture, template detection, the CPU micro-program on the fast tree) + serial live case "RUN FAST takes the state over…" (RAM word + register taken over, Registre B loaded through the inputs in fast mode, an edit leaves, the gates get everything back, cache saved, a chip switch leaves) + a self-test check (`FastVerify.Compare` on the fixture CPU over 200 half-periods, cache file round trip). Checked to fail with: a corrupted table, a corrupted register model, no write-back, no exit on edit. `FastVerify.Compare` / `FastBench` compare every top-level output just before each edge (driven bits and floating mask; the bits of a floating line are leftovers). `FastDiag.cs` prints, per template candidate, where it failed against the gates.

### LCD DEM122032A (graphic LCD, 122 x 32, black and white)

`ChipType.LcdDem122032` (appended to the enum; name "LCD DEM122032A"; DISPLAY collection + `LateAddedBuiltins`, so existing projects get it). User, 2026-10-03: the REAL component's interface, not a simplified one. Model in `Simulation/LcdDem122032.cs` (shared by the gate, the drawer, the test harness and the bench): two SED1520 controllers, E1 = left half (columns 0-60 → x 0-60), E2 = right half (→ x 61-121); per controller a display RAM of 4 pages × 80 columns (a byte = 8 vertical pixels, bit 0 at the top of the page) and registers (page, column, start line, on, ADC, static drive, read-modify-write, output latch, last E). Pins: inputs `DB` (8), `A0` (0 = command/status, 1 = data), `R/W` (1 = read), `E1`, `E2`, `RES`; output `DB OUT` (8) — the module's bidirectional bus is an input + a 3-state output, driven only while a read is enabled (R/W = 1 and E high), floating otherwise, so it can sit on a bus. 68-series timing: a write is taken on the FALLING edge of E; a read drives the output while E is high and its side effects happen on the fall (latch ← RAM, column + 1 except in RMW), which gives the real "dummy read". Commands: AE/AF display off/on, B8+p page, 00-4F column (auto-increment after each data byte, wraps at 80), C0+l start line (vertical scroll), A0/A1 ADC normal/reverse, A4/A5 static drive, E0/EE read-modify-write / end, E2 reset (start 0, column 0, page 3); A8/A9 duty ignored (the module is 1/32). Status: D6 = ADC normal, D5 = 1 when the display is OFF. Deviation: `RES` is a level, 1 = reset (an unconnected RES reads 0, so the module runs). Power-on: display OFF, RAM random (seeded `Simulator.NextBytes`) as on the real module. Stateful (`MemorySnapshot`, `CircuitExporter.StatefulBuiltins`), described for Ask Claude in `CircuitExporter.BuiltinDesc`, reported by `test_sequence` as 16 text lines (`CircuitTester.ReadLcdGrid`, half-block characters). Drawn by `DevSceneDrawer.DrawDisplay_Lcd` (Scale = width, height = width × 32/122, STN colours). ### QA / debug harness (`Game/Project/CircuitTester.cs`)
Lets the assistant (and the truth-table view) **run the real simulator on an isolated copy** of a chip, so it can verify its own work; the live circuit and the sim thread are never touched.
- `BuildIsolatedSim(liveDesc, lib)` wraps the chip as the single subchip of a throwaway harness (the simulator only processes *subchips*, never the root's own logic) and resolves it under a temp name through `ChipLibrary.SimOverride` — so it simulates the **live, possibly unsaved** description and works for a never-saved chip too. `TruthTableComputer` uses the same builder (fresh sim per row).
- **Clock in tests**: no real time passes in the harness, so the builtin CLOCK (whose level is `simulationFrame / stepsPerClockTransition`, i.e. 250 ticks per transition) would never toggle over a few ticks. `Simulator.forcedClockState` (-1 = normal, 0/1 = forced; reset in `Simulator.Reset` and in the harness `finally`) pins every clock chip, so a test **drives** edges: `clocks: N` on a step plays N full cycles (LOW→HIGH per cycle, then a final LOW settle) and `set {pin:"CLOCK"}` sets the level by hand. All clock chips share one phase in this simulator, so a single global level is faithful — including clocks nested in sub-bricks (`ContainsClock` walks the sim tree). When a tested circuit contains a clock and the sequence never drives it, the report says so explicitly; the truth table pins the clock to 0 for determinism. `clocks` also drives an **input pin named like a clock** (CLOCK/CLK/HORLOGE exactly, else the single 1-bit input containing one of those words — `IsClockName` / `LooksLikeClockName`): a chip built from latches (the user's `Bascule D`) has an input `Clock` and no CLOCK component, and `clocks:1` used to be silently ignored there, after which the assistant declared the circuit broken and invented a timing explanation. The report header now states what `clocks` drove (component, input, both) or that it was ignored, and the prompt tells Claude to read it and never invent timing stories. In a step the `set`s are applied before the cycles, so "set D + clocks:1" is correct. This exists because Claude otherwise "fixes" the dead clock by rewiring the circuit (disconnecting CLOCK, adding test inputs) — the prompt now forbids that.
- `RunSequence` = the `test_sequence` tool: applies a list of steps (`set` input values, then N ticks) and reports, after each step, output pins + everything **visible** on the chip face — LED ON/off, 7-segment (decoded to the character it forms, else the lit segments), RGB/dot displays as a 16×16 ASCII grid (only reprinted when it changes), plus optional internal probe pins (`watch`). Sim state persists between steps, so sequential circuits (latches, counters, RAM) behave as in the app. Report only ever mentions things that exist (no "no LED" filler) — keep it token-lean.
- Displays are enumerated exactly like `DevSceneDrawer.DrawDisplay` (builtin display chips placed directly + displays exposed on a custom sub-chip's face, recursively), resolved in the sim by their subchip-ID path.
- KEY chips are pressable: `SimKeyboardHelper.SetVirtualKeys` overrides the real keyboard for the duration of a test (always cleared in `finally`, and in `UnityMain.ResetStatics`).
- Everything runs with the sim thread parked via `Project.RunWithSimulationPaused`. The harness builds its own tree (its own `SimProgram`), and the per-run `Simulator` statics are thread-static, so the live simulation's state is never disturbed.
- The system prompt makes testing **mandatory** before Claude declares a module finished (truth_table if combinational, test_sequence if sequential).
- The system prompt has a **strict scope rule** ("PERIMETRE"): do exactly what is asked and nothing more — no unrequested fixes, no "while I'm at it" wiring, no tidying; anything else noticed is reported in one line, not acted on. Added after "relie les reset" on an 8-bit register also wired the data lines. The quick-mode note asks for the narrowest reading of an ambiguous request.

### Editing circuits programmatically (used by the tools; reusable)
- `DevChipInstance.AddNewSubChip / AddNewDevPin / AddWire / DeleteWire / DeleteSubChip` mutate the dev chip **and** enqueue the matching `Simulator.Add*/Remove*` so the sim thread stays in sync (never touch `SimChip` from the main thread directly). ### Editor quality-of-life
- **Layout constraints** (`LayoutCol` / `LayoutRow`, 0 = automatic): optional per-element hints honoured by Clean Up, set via the `set_layout` tool. `LayoutCol` (≥1) forces the column (bigger = further right, equal = same column, overrides the depth-based placement); `LayoutRow` orders within a column (bigger = higher) **and** aligns elements of *different* columns that share the same value onto one horizontal line (the column is shifted as a rigid block, so spacing/overlaps are untouched). Unconstrained elements keep their relative order — their sort keys are interpolated between the constrained ones — so a chip with no hints lays out exactly as before. Fields live on `SubChipDescription` / `PinDescription` (and on `IMoveable`), so they persist; they are purely additive and default to `0`, so **no save-format migration and no `DLSVersion` bump** (bumping would make every open chip look dirty, since `HasUnsavedChanges` diffs the serialized description).
- `Game/Interaction/CircuitAutoLayout.cs` — **Clean Up**: lays subchips in columns by signal-propagation depth, sorts dev pins **by name group, biggest number on top (A.. before D..; D4, D3, D2, D1, D0 — `PinOrderCompare`)**, orders each subchip column with **barycenter sweeps** (fewer wire crossings, and the remaining ones spread out rather than piled up), grid-snaps, and routes wires with **as few bends as possible**: a wire tries a straight line, then one bend (diagonal + horizontal lead into the target, or lead out of the source + diagonal), then two bends (lead-diagonal-lead) — first candidate that clips nothing and overlaps nothing wins. Only a pin feeding ≥ `TrunkFanOut` (3) wires gets a vertical **channel** in the gap after its column (gaps widen to fit; the topmost pin takes the farthest channel so leads nest): its wires go lead → shared channel (trunk, the only overlap allowed) → horizontal branch at the target's height. That is what keeps a fan-out-heavy circuit (ALU4: 8 inputs → 4 chips) readable as a regular grid instead of a heap of diagonals, while everything else stays direct. A wire whose branch would clip a component of a column it spans (or that runs backwards) gets a detour above/below the obstacle band on the nearest free track; wires from the same column to the same component are routed as a **group** (one side, nested tracks) so they travel together. **Wires may cross but never overlap** (`CollinearOverlap` check against every segment already laid). Wire **junctions** (a wire starting on another wire) are converted to direct pin-to-pin wires first (`RemoveConnectionDependency`): the trunk routing renders fan-out anyway, and a junction's stale points were what scrambled chips like the D latch (`VerrouD`) after the components moved. A `CleanUp: …` line in `Player.log` reports wires/detours/remaining overlaps. **Undo**: `UndoController.LayoutSnapshot` records every position and every wire's points before/after, so Ctrl+Z restores the exact previous layout (a plain move record would lose the wire points). ### Circuit optimisation tools (bottom-bar right-click on a chip)

Three entries, all enabled only for a **custom** chip (a builtin is refused); `Optimise` additionally
requires the chip to be **combinational**.

- **`Count nand`** (`Game/Project/NandCounter.cs`) — total NAND needed to build one instance, expanding
  custom sub-chips recursively. Non-decomposable builtins (clock, RAM, displays, KEY, VCC/GND) are
  listed separately; buses and merge/split are not counted (pure wiring, zero gates).
- **`Nand only`** (`Game/Project/NandFlattener.cs`) — flattens the whole hierarchy into one chip of
  builtin primitives. Pure netlist operation: a `WireDescription` is only "source pin -> target pin"
  (`ConnectionType` is routing, `Simulator.BuildSimChipRecursive` ignores it). Each inlined chip's
  interface pin becomes a virtual node that is resolved away, so a signal crossing several levels
  becomes one direct wire. Buses vanish too (a bus origin is a pass-through, a terminus a dead end).
- **`Optimise`** (`Game/Project/GateMapper.cs`) — opens the package palette
  (`Graphics/UI/Menus/GatePaletteMenu.cs`), then rebuilds the chip out of the ticked packages while
  **minimising the number of packages**. Hierarchy is flattened on the way in, so it works directly on
  a chip built from sub-bricks.

#### The pipeline

`NandMinimizer.ReadAsNandNetlist` (flatten if needed, then `Extract` to an AIG) -> AIG rewriting +
don't-cares -> cut-based technology mapping -> bin-packing -> local search -> emit -> **verify**.

- `AigCore.cs` — the shared AIG: literals (`node*2 + complement`), structural hashing with constant
  folding, 4-input cut enumeration, the minimal-structure library, and bit-parallel equivalence
  checking. Node 0 is the constant, nodes `1..NumPI` the inputs.
- `AigDontCare.cs` — observability don't-cares, computed **exactly** (simulate the whole circuit twice,
  once with the node flipped, XOR the outputs). A node may be replaced by anything that agrees with it
  wherever it is observable.
- `NandMinimizer.cs` — DAG-aware rewriting (Mishchenko/Chatterjee/Brayton, DAC 2006), alternating with
  the don't-care pass until neither finds anything.
- `GateMapper.cs` — cut-based mapping (Chen & Cong's DAOmap scheme), then `Repack` and `LocalSearch`.
- `GatePackages.cs` — the palette. Each line is a package type (gate kind + gates per package);
  several lines may hold the same gate, in which case the effective capacity is the largest.
- `ChipEmitHelper.cs` — shared plumbing for building a `ChipDescription` from scratch.

#### Things that are easy to get wrong here

- **The objective is NAND gates, not AIG nodes.** A NAND computes `~(a&b)`, so an AND node whose output
  is *also* needed uncomplemented costs an extra inverter. Driving the search on node count alone makes
  circuits WORSE (a 4-NAND XOR "optimises" to 3 nodes + 3 inverters = 6 gates). `MappedCost` is the
  real metric everywhere.
- **The package objective is a sum of ceilings**, which no linear per-gate weighting can express. Two
  passes exist precisely for it, and both were measured to pay: `Repack` (a gate can be taken from
  another package type — an inverter is a NOR with its inputs tied — so emptying a nearly empty type
  removes a chip) and `LocalSearch` (re-implement one signal with a runner-up cut, judged on the true
  cost). On an 8-bit ALU they gave 38 -> 37 -> 36 packages.
- **Don't-care gating must budget the real cost**, not the input count. A flat "16 inputs max" silently
  disabled the pass on a 19-input ALU — the single biggest loss measured (42 -> 38 packages once fixed).
  Cost is `nodes x words` in memory and `nodes^2 x words` in time; both are budgeted in `Applicable`.
- **Generated chips must be registered in `ProjectDescription.AllCustomChipNames`.** It is the only list
  the loader rebuilds the library from — it does not scan `Chips/`. Starring a chip rewrites the
  description untouched, so a generated chip saved that way comes back invisible: present on disk,
  unusable, and undeletable (`DeleteChip` threw). `ContextMenu.CommitGeneratedChip` calls
  `UpdateAndSaveProjectDescription()` for this reason, and `Project.DeleteChip` now tolerates a chip
  missing from the library.
- **Generated chips must not look "modified" when opened.** `HasUnsavedChanges` diffs the serialized description, and a `SubChipDescription` written with `OutputPinColourInfo = null` differs from the live one (an entry per output pin). `ChipLibrary.FillMissingOutputPinColours` fills the defaults on load and on `NotifyChipSaved` (buses excepted). `Assets/Editor/DirtyCheck.cs` (`-executeMethod DirtyCheck.Run -benchProject "PC"`) reloads every chip of a project and prints the first JSON difference — run it whenever the red star shows up on a freshly opened chip.
- **Nothing is ever written before verification.** Every generated chip is read back from its own
  description (slot by slot for packages, so the emitted wiring itself is checked) and compared to the
  original over the whole input space — exhaustively up to 20 inputs, sampled beyond, and the report
  says which. A mismatch aborts and creates nothing.
- **Unconnected input pins read LOW** in the simulator, so `Extract` models a missing driver as
  constant 0. Two wires into one pin makes the result order-dependent, and is refused.
- Generated package bricks are named `4xAND2`, `6xNOT`, `1xNOR2`… A one-gate 2-input NAND package *is*
  the builtin NAND (no wrapper brick). An existing chip of the same name is reused **only** if its
  interface and function are verified identical, otherwise a suffixed name is taken.
- Statics added here must be reset in `UnityMain.ResetStatics()`: `GatePackages.Reset()` and
  `GatePaletteMenu.Reset()` are. `AigLibrary`'s table is a pure immutable cache and is deliberately not.

#### Measured dead ends — do not redo these

Each was implemented, measured on the ALU project, and removed because it gained **nothing**:

- rebuilding the circuit from its truth tables (BDD / Shannon, several variable orders) — 0, 50x slower;
- structural choices (ABC's `dch`: merge several structures, group equivalent nodes, let the mapper mix
  cuts across them) — 0, even with 94 multi-member classes on the ALU;
- two-divisor resubstitution in the don't-care pass — 0, 8x slower;
- banning a package type outright, marginal-cost feedback, fill-informed "squeeze" weightings,
  multi-start local search, longer optimisation loops;
- a 5x wider mapper search (500 weightings, 25 s budget) — 0 on every circuit.

The lesson: search effort is **not** the limiting factor, and neither is the AIG structure. Every real
gain came from the don't-care pass or from the two package-aware passes.

#### Simulation speed bench

`Assets/Editor/SimBench.cs` (`-executeMethod SimBench.Run -benchProject "PC" -benchChip "CPU" [-benchSet "PIN=v,..."] [-benchToggle <pin>] [-benchScenario cpu] [-benchBatch 1] [-benchSettle 1]`) builds the isolated sim of a chip, counts the sim tree and times 500 / 2000 steps, reporting how many gates each step actually ran. Since the core skips unchanged gates, **only an active scenario is meaningful**: `-benchScenario cpu` drives the user's CPU through a micro-program in a loop (A = A + 1; MAR = A; RAM[MAR] = A, clock edges included — registers, ALU, bus, decoders and RAM all work every cycle), `-benchToggle <pin>` flips a 1-bit input every step, `-benchSet "PIN=v,..."` holds inputs. The tree walker visited every chip every step, so its cost did not depend on activity. Measured 2026-09-27:

| chip, scenario | sim tree | tree walker | compiled, every gate | compiled, changed gates only |
|---|---|---|---|---|
| `CPU`, micro-program loop with clock | 63 322 chips, 44 662 gates, 213 294 pins | 7.9 ms/step, ~127 steps/s | 0.35 ms/step, ~2 900 steps/s (idle; same for any activity) | 0.017 ms/step, ~58 000 steps/s (433 gates run per step) |
| `ALU8`, input A toggling every step | 2 170 chips | 0.094 ms/step, ~10 600/s | 0.0035 ms/step, ~296 000/s | 0.003 ms/step, ~370 000/s (100 gates/step) |
| `Registre8`, clock toggling every step | 444 chips | 0.016 ms/step, ~62 000/s | 0.001 ms/step, ~940 000/s | 0.002 ms/step, ~500 000/s (85 gates/step) |
| `CPU` as the user runs it: builtin CLOCK, 70 steps per tick, control lines held (`-benchSet "OE_ALu=1,OP1=1,Load_A=1,We_RAM=1,Reset_all=0"`) | same | 9.5 ms/step, 105 steps/s = 0.75 Hz clock | — | 0.003 ms/step, 321 000 steps/s = 2.3 kHz clock (26 gates/step); with idle skipping (`-benchBatch`, what the live thread does) and the input values SAVED in the chip (`PinDescription.InputState`, exactly what the app simulates — the user's montage holds OE_ALu, Load_A, OP1, Load_MAR, We_RAM): 1 170 000 steps/s = 8.3 kHz, matching what the user reads in the app; then 2 000 000–2 200 000 = 15 kHz with the NAND wake-up filter and the NAND+inverter fusion, then 2 600 000–2 800 000 = 19 kHz with common-gate elimination of NANDs, then 3 500 000–4 900 000 = 25–35 kHz once the 256 RAM word splitters (all splitting the same bus) merge too (5 % of the steps are real, ~75 gate runs per real step at ~55 ns all-in). The spread between runs comes from the random pick at the CPU root level (bus loop), which changes the settle path; the merge count itself is deterministic (3 686). (With the hand-picked `-benchSet` above, without Load_MAR: 538 000 = 3.8 kHz. An earlier 865 000 was measured with unset inputs left floating, which the app never does: the bench now drives every input like the app, saved value or 0.) |

`-benchTrace` prints the gates run on 6 consecutive steps (with their chip path), `gate runs per step by chip` in the normal run says which chips do the work, `noise readers` which gates read a floating line. On the user's CPU between two edges NOTHING runs (idle); the cost is at the edges: the bus change wakes the 256 RAM words (split + 2 latch NANDs each, ~800 gate runs) and the register/ALU settle takes ~20 steps × ~50 gates. `-benchSettle` measures, over 40 clock edges, how many steps the chip's pins keep changing after an edge — the minimum "steps per clock tick" the montage needs. The user's CPU: worst 11 steps (most edges settle in 0–4), so 13 is safe where the user had 70: a free ×5 on the clock frequency, the user's call.
The tree-walker column was measured on the SAME scenarios by checking the pre-rewrite commit (`b848523`) out into a separate working copy (`git worktree add ../old b848523`) with a copy of this bench's scenario code using the old `PinState.Set(ref ...)` API — a fresh working copy needs a few minutes of asset import on first open.

A gate that runs costs about 30–40 ns (its output write marks its consumers); a gate that does not run costs nothing. Small chips gain little from skipping (everything is active); the CPU gains ×20 more because most of its 44 000 gates are idle at any given step.

#### Regression bench

`Assets/Editor/NandBench.cs` (editor-only, nothing written to disk):

```
Unity.exe -projectPath <proj> -executeMethod NandBench.Run -benchProject "ALU" [-benchChip "ALU8"] -quit -logFile <log>
```

It flattens every chip of a project, optimises each twice (bare NANDs, then the full palette), runs
palette scenarios (including "only a 1-gate package" and "XOR only", which must be refused), checks
that no unticked package is ever used, and verifies every result against the original. It exits
non-zero on any failure. It caught both the deletion bug and the NAND-only gap — run it after any
change to these files.

#### Runtime limits worth knowing

Unity's **Mono** backend, .NET Standard 2.1 (`scriptingBackend Standalone: 0`). No
`System.Numerics.BitOperations`, no `System.Runtime.Intrinsics` — which matters, because the hot loops
(don't-cares, equivalence checking) are pure 64-bit word operations that AVX2 would do 4x faster. The
don't-care pass is parallelised over input-pattern ranges (`Parallel.For`), which took an 8-bit ALU from
11.8 s to 4.6 s. If speed becomes a problem again, flatten `ulong[][]` to a single `ulong[]` first.
